DESCRIPTION

Create a new PyTorch compiler with an MLIR-based pass pipeline to perform
specific optimizations described herein while providing functionality to
achieve compiled execution via torch.compile.

The new compiled approach should be activated with:

`torch.compile(backend="e0358", ...)

Use the torch_xla framework to import torch into stablehlo MLIR.

See broadcast-n-consumers.py and truncate-n-consumers.py (described below) to
use as starting points.

Put together a lowering and optimization pipeline from stablehlo into LLVM/NVVM
for GPU execution, and perform the JIT execution via torch.compile.

Use and extend the affine fusion framework to ensure the pass pipeline above
performs the following kind of fusion as well: for a broadcast that has 'n'
consumers, ensure that the broadcast is fused into each of the 'n' consumers.
However, for truncating nests or nests with a non-trivial computation, such a
fusion is detrimental. Check and disallow such fusion.

The fusion should be performed on the affine + memref dialect abstractions in
MLIR.

Test case 1 (fusion expected): broadcast-n-consumers.py broadcasts a 4096x128
float32 tensor to 4096x128x32 and consumes the result in 8 pointwise
multiplications, each with a different 4096x128x32 tensor. All 8 outputs are
verified against eager execution. Run it with:

  python broadcast-n-consumers.py                    # Inductor (reference).
  python broadcast-n-consumers.py --backend e0358    # Your backend.

With the expected fusion, the 4096x128x32 broadcast result should not be
materialized in memory; Inductor, for example, generates a single fused kernel
for this test case.

Test case 2 (fusion NOT expected): truncate-n-consumers.py truncates a
4096x4096 float32 tensor to float16 and consumes the result in 8 pointwise
multiplications, each with a different 4096x4096 float16 tensor. All 8 outputs
are verified against eager execution. Run it with:

  python truncate-n-consumers.py                     # Inductor (reference).
  python truncate-n-consumers.py --backend e0358     # Your backend.

Here, the truncation is a non-trivial computation whose result is half the
size of its input. Fusing it into its consumers would replicate the float32 ->
float16 conversion in all 8 consumers, and each consumer would then read the
float32 input (twice the bytes of the float16 result) instead of the truncated
tensor. Your backend should detect this and not fuse: the float16 result
should be materialized once and read by all 8 consumers.

Both scripts share their command-line parsing, backend lookup, verification
against eager execution, and timing via common.py. The scripts import a module
named 'e0358', which should register the backend with torch._dynamo (e.g., via
torch._dynamo.register_backend(name="e0358")).

Use the LLVM version at tag 23.1.3 as the base for all your MLIR work.
https://github.com/llvm/llvm-project/releases/tag/llvmorg-23.1.3 All your MLIR
additions should be submitted as a single git commit patch (use git format-patch
HEAD~ with your commit on top of the above LLVM version).

Your LLVM patch should have been formatted with clang-format (git clang-format
HEAD~).

For stablehlo, use stablehlo at commit 965c428908be23f05e80e3c8e7f0b1a806ac3751
dated 2026-08-04 which will build correctly against the above LLVM version.
Your assignment shouldn't normally need any patches/changes to stablehlo.

All Python code submitted should be formatted with black and wrapped at 80 cols.
